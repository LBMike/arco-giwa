# GIWA Stocks 어드민 기획 v1

2026-09-16. 사용자의 최종 개발 순서는 GIWA 완성 후 XRPL이다. 이 문서는 운영 화면의 기획이며 화면 구현이나 테스트넷 배포 완료를 뜻하지 않는다. 백엔드는 별도 `STOCKS-GIWA-001` 작업에서 개발한다.

## Ondo에서 확인한 것과 확인하지 못한 것

Ondo 내부 어드민의 실제 화면과 메뉴 구조는 공개 자료에서 확인하지 못했다. 다음은 공식 공개 운영 인터페이스이며, 아래 ARCO 화면 구성은 이를 참고한 제안이다.

- 서명된 견적으로 발행·상환하고 사용자·종목·만료·중복 사용·한도를 검사한다. 공개 EVM 인터페이스의 원자적 토큰 교환은 확인되지만, 각 사용자 요청마다 새로운 브로커 주문이 먼저 체결되는지는 공개되지 않았다. https://docs.ondo.finance/api-reference/smart-contracts
- 전체·사용자·종목별 거래 한도와 미사용 견적의 한도 점유를 관리한다. https://docs.ondo.finance/api-reference/limits/get-trading-limits
- 시장 전체 상태와 개별 종목 중지·제한을 구분하고 기업 이벤트의 영향을 표시한다. https://docs.ondo.finance/api-reference/status/get-asset-statuses
- 보유 자산과 NAV 보고, 대사와 외부 검증을 설명한다. https://docs.ondo.finance/ondo-stocks/trust-and-transparency

ARCO의 초기 `모의 브로커 체결 → 발행` 비동기 흐름은 우리의 테스트넷 설계이다. Ondo 내부 구현과 같다고 표시하지 않는다.

## 첫 화면

흰색 테마, 데스크톱 최대 폭 1512px, 왼쪽 탐색 메뉴를 유지한다. 기존 디자인 문서의 어두운 어드민 테마보다 사용자가 정한 흰색 테마를 우선한다.

상단에는 서버가 확인한 환경을 표시한다: `GIWA Testnet · Mock broker · Test assets`. 배포 식별자, 마지막 갱신 시각, 데이터 지연 여부를 함께 제공한다. 브라우저 문구만으로 환경을 판단하지 않는다.

첫 화면의 중심은 처리할 사건 목록이다. 발행 대기·결과 미확정·입금 예외·지급 대기·잔액 차이·데이터 지연을 보여준다. 행마다 발생 시각, 경과 시간, 종목, 주문 식별자, 막힌 단계, 마지막 증거와 가능한 다음 행동을 제공한다. 조회 실패나 오래된 데이터는 0건으로 표시하지 않는다.

| 메뉴 | 주요 정보 | 첫 버전의 범위 |
|---|---|---|
| 운영 현황 | 미완료 주문, 발행 대기, 입금 예외, 연결 상태 | 조회와 주문 상세 이동 |
| 주문 | 사용자 지갑, 주문 수량·금액, 체결·체인 상태 | 필터, 목록, 상세 타임라인 |
| 종목·토큰 | 40개 목록, 실제 활성 종목, 토큰 주소·공급량·한도 | 배포/거래 가능 여부를 구분한 조회 |
| 발행·회수 | 요청별 거래 해시, 확정 블록, 실패·미확정 사유 | 주문에 연결된 증거 조회; 회수는 해당 백엔드 완료 후 활성화 |
| 잔액 대사 | 모의 보유 자산, 체인 공급량, DB 기록, 진행 중 수량 | 차이와 비교 기준 시점 조회 |
| 권한·감사 | 운영자, 변경 요청·승인, 사유·결과 | 감사 조회 먼저; 변경 권한은 후속 단계 |

처음 개발할 화면은 운영 현황, 주문 상세, 잔액 대사, 감사 이력이다. 활성화되지 않은 메뉴는 모의 성공 데이터를 만들어 보여주지 않는다.

## 운영 권한

정상 주문은 정책 안에서 자동 처리한다. 모든 주문마다 사람의 승인을 요구하지 않는다.

- 조회자는 상태와 증거를 읽는다.
- 운영자는 허용 범위 내 신규 주문 중지나 지정된 복구를 요청한다.
- 승인자는 다른 사람이 만든 재개·한도 변경 등의 정확한 요청을 승인한다.
- 실제 서명은 분리된 서명 서비스가 수행한다. 개인키 입력·업로드 화면은 만들지 않는다.

긴급 중지는 신속하게 적용하고 재개는 다른 운영자의 확인을 요구한다. 중지 중에도 기존 거래 조회, 대사, 감사 기록은 계속된다. 백엔드는 매 명령마다 권한·대상 환경·버전·사유·멱등성을 검증한다. 화면의 버튼 표시 여부는 보안 경계가 아니다.

주문 없는 임의 민팅, 잔액 직접 수정, 주문 강제 완료, 결과가 불명확한 거래의 새 거래 재전송은 제공하지 않는다. 테스트 자금 공급·모의 체결 조작·실패 주입은 일반 운영 화면과 분리된 테스트 도구이다.

## GIWA 개발 순서

1. 기존 DB 검사기 수정과 회귀 검증. 기존 이력·배포는 그대로 둔다.
2. NVDA 1종목의 테스트 입금 → 모의 체결 → 발행 증거 검증, 주문·원장·재시도·조회 API.
3. 별도 Stocks 컨트랙트와 서명 경계, 기존 로그인 연결, 실제 GIWA 테스트넷 거래 검증.
4. 매도 토큰 보관 → 모의 매도 → 소각 → 테스트 자산 지급·미체결 반환.
5. 어드민 제어 명령과 UI, 3종목 검증 후 40종목 확대, 기존 Saving/Funds 회귀 검증.
6. GIWA 흐름 완료 후 XRPL 발행·지갑·확정성 연동을 독립 작업으로 시작.

실제 Alpaca 계정 연동은 별도 작업이다. 모의 브로커와 실제 체인 증거를 구분하고, 테스트넷 토큰을 실제 주식 소유권으로 표시하지 않는다.

## UI 연결 계약

백엔드 작업의 기준 경로는 `/api/v1/stocks/*`, `/api/v1/admin/stocks/*`다. 완성된 DTO와 오류 상태는 `docs/contracts/stocks-giwa-v1.md`의 검토된 버전을 기준으로 Claude에 전달한다. 이 문서의 기획만 보고 임의 API나 성공 상태를 구현하지 않는다.

기존 GIWA의 단일 관리자 토큰은 개별 운영자 신원이나 2인 승인을 증명하지 못하므로, 새로운 Stocks 변경 명령의 권한으로 자동 승격하지 않는다. 첫 백엔드 버전은 식별된 운영자 resolver를 주입받는 조회 API부터 제공한다.

# Trusted submission receipt reconciliation

POST `/api/v1/stocks/wallet-submissions/reconcile` uses existing authenticated owner resolution and no-store/profile response. Exact body: `{claimId,intentKey,stage,transactionDigest,txHash}`. The hash must already be recorded durably; requests cannot supply transaction details, proof, terminal status or another owner. Response remains AttemptRecord, adding CONFIRMED and REVERTED. Missing/not-finalized receipts return the current status. Fixed 503 errors: SUBMISSION_RECEIPTS_UNCONFIGURED, SUBMISSION_RECEIPT_UNAVAILABLE, SUBMISSION_RECEIPT_TIMEOUT. Neither proof nor RPC error details are exposed.

`createSubmissionReceiptVerifier(manifest, rpc)` in `server/src/stocks-submissions/receipts.ts` supplies the optional second StocksSubmissionsService constructor argument. The manifest is validated and frozen. Verification checks chain/network/checkpoint, exact transaction hash/from/to/input/value, canonical finalized receipt block and all five configured code identities. Approval additionally requires exactly one matching token Approval event with exact owner/spender/bounded amount. Funding and escrow reuse the existing ReceiptVerifier semantic helpers, including exact token movement and composite escrow identity. Reverted receipts require the same transaction/network/finality/code binding and zero logs. Final block/checkpoint rechecks reject observed reorgs. Existing success-only ReceiptVerifier.fetch is unchanged.

The factory uses an eight-second total verification deadline, zero retries and at most 16 ChainPort calls, sequentially scheduled. The existing ChainPort cannot accept AbortSignal: a dispatched transport request may still finish after the deadline. Its result is discarded, later reads stop and verification cannot write to the database. The optional timeoutMs argument is a shorter test/integration bound only (integer 1..8000); it cannot extend the limit. This is the verification deadline, not a guarantee on pool acquisition or database commit latency. No database transaction holds a lock while RPC verification runs.

Reconciliation first validates current owner/order/deployment/hash under locks, verifies through the trusted server port, then rechecks ownership and immutable binding in a separate transaction. Proof insertion, terminal status and audit commit atomically. Database triggers enforce initial REQUEST_MAY_START, proof/claim/envelope binding, append-only proof and no terminal downgrade or hash mutation. A terminal UPDATE requires a matching persisted proof; application client outcomes cannot create one. Late UNKNOWN/SUBMITTED observations return the existing terminal state. Concurrent reconciliations produce one persisted proof/audit and return the winning terminal record.

A new TRANSFER claim may follow APPROVAL only when its status is CONFIRMED and the matching persisted proof exists. Other first-claim checks remain: trusted enrollment, actor/wallet/deployment, readiness/pause, payable state and database deadline. A reverted approval never unlocks transfer. APPROVAL cannot follow an existing TRANSFER and same-stage claims remain null duplicates. Transfer confirmation does not change Stocks order state or perform ledger settlement. Existing controlled-wallet preflight and a separate transfer action remain necessary; this endpoint never sends a transaction.

Trust relies on the configured server ChainPort; deterministic fixtures do not establish live RPC correctness. Finalized proof remains immutable after acceptance; later chain failure or catastrophic finalized reorg requires a separately designed operator procedure, not client downgrade. Direct raw contract calls outside the application gate remain outside this protocol.

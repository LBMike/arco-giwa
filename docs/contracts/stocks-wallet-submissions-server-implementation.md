# Stocks wallet submissions server implementation

Implements `stocks-wallet-submissions-v1.md`; no API revision. Composition belongs to the integration owner. Export `StocksSubmissionsService(stocksService)` from `server/src/stocks-submissions/service.ts` and `stocksSubmissionsPlugin` / `StocksSubmissionsPluginOptions` from `plugin.ts`. Inject the established trusted actor resolver; unauthenticated requests are rejected before body parsing. Responses use the seven-field PROFILE/observedAt/data envelope and no-store.

New BUY/SELL USDC orders atomically insert immutable enrollment before the enclosing transaction commits. Existing-order idempotency paths never enroll. The additive migration intentionally does not backfill historical orders: an absent submission journal cannot establish that a wallet was never invoked. Enrollment binds side, order, wallet, actor, current deployment and immutable order snapshot. Deploy the additive migration before using the new order-creation hooks. Existing RLUSD order creation retains its prior behavior and is outside this USDC wallet protocol.

A physical intent is SHA256 of canonical JSON `[91342, spenderLower, tokenLower, walletLower, orderKey]`; actor and deployment aliases do not create another physical slot. The existing ABI determines exact bounded approval/deposit/escrow transactions. A physical advisory transaction lock serializes both stages and a database unique key backs each stage. Only a newly committed insert returns REQUEST_MAY_START; duplicate requests return null. Commit and audit failure roll back together. The caller must inspect after an ambiguous response instead of repeating wallet execution.

Existing TRANSFER prevents later APPROVAL. Existing APPROVAL blocks TRANSFER until trusted reconciliation persists a matching CONFIRMED proof; see stocks-wallet-receipts-server.md. Reverted or pending approval remains blocked. Client CONFIRMED/REVERTED is rejected. UNKNOWN and SUBMITTED are observations, with immutable transaction hashes and monotonic SUBMITTED state. Pause, deadline and payable-state checks gate first claims; inspect/outcomes preserve recovery after pause or expiry. Claim/enrollment deletion and truncation are rejected by database triggers. Direct calls to raw contracts outside this application are not prevented by this gate.

This implementation performs no signing, broadcast, allowance RPC, operator settlement, deployment or public activation. The optional trusted receipt verifier is described in stocks-wallet-receipts-server.md. A successful journal claim is permission for one controlled wallet request, not evidence of execution or confirmation. Actual application registration and browser integration are verified separately by the integration owner.

## Isolated verification

Build with `npm run build:server`, then execute `node scripts/stocks-submissions/test-postgres.mjs`. The harness creates a new Unix-socket-only PostgreSQL instance, applies the two existing Stocks migrations and the additive submission migration to a fresh schema, runs the dedicated suite, persists a claim across a real PostgreSQL restart and a new Node process, and shuts down in finally. On this host run the harness outside the sandbox with the approved escalation; sandbox initdb cannot allocate the required IPC correctly. It never reads a configured application database URL.

Additional explicit compiled `.test.js` or `.mjs` files inside the same checkout can be passed as arguments. The harness supplies `STOCKS_SUBMISSIONS_TEST_ONLY`, `STOCKS_SUBMISSIONS_TEST_DATABASE_URL`, `STOCKS_TEST_HARNESS_ONLY`, and `STOCKS_TEST_DATABASE_URL` pointing only to its owned socket. `STOCKS_PG_BIN` can explicitly select an installed PostgreSQL binary directory. No installation is performed. Temporary evidence and PostgreSQL logs are preserved at the reported owned path after shutdown.

# Stocks canonical digest locale compatibility

The shared backend canonicalJson recursively sorts own enumerable object keys using `a.localeCompare(b, 'en-US')`, preserves array/value order, and JSON.stringify serializes the result. SHA-256 over those UTF-8 bytes supplies manifestDigest, callDigest, submission transaction/proof/intent/enrollment digests and durable mock-broker requestDigest. ABI_DIGEST and operationKey use separate existing serialization and are unchanged.

The locale is explicit to preserve the existing en-US digest format when the host default locale is Czech, Slovak or another locale. Default-locale ordering incorrectly moves `chainId` and `checkpoint*` keys under cs/sk. This is a compatibility repair, not a new digest version or a code-unit/JCS canonicalization migration. No alternate legacy digest is accepted and no existing record is rewritten.

Pinned test vectors were captured before the change from backend c97c5c9775572ace1d5510356c2f710b562c364f under en-US, Node v24.14.0 / ICU 78.2. Tests run actual fresh Node processes with en-US/cs-CZ/sk-SK defaults and compare fixed bytes/digests, including recursively reordered JSONB-like objects. They include supported manifest, BUY approval/transfer transaction, intent, enrollment, signer, trusted approval receipt and BUY/SELL broker shapes, plus mixed-case/punctuation/Unicode and nested generic objects. Explicit en-US preserves those old hashes. Code-unit sorting does not preserve all arbitrary-key examples, so it is deliberately excluded.

Intl collation still depends on the runtime's ICU implementation/data. This change removes host-default-locale dependence; it does not guarantee equality across every future ICU/browser version. Keep golden vectors immutable, record runtime versions, and verify them when changing runtime support. Distinct arbitrary Unicode keys can also compare equal under en-US (for example composed/decomposed accented forms), retaining legacy insertion-order ties. No tie-breaker or Unicode normalization is introduced because either can change old hashes. The Stocks schema-owned field/address key sets and the pinned generic vectors are covered, not every possible JSON object. A future version-independent canonical format needs its own compatibility review.

Persisted deploymentDigest scopes quotes/orders/ledger/provider/journal records. Enrollment orderBinding, submission transactionDigest and receipt proofDigest protect immutable facts; signer callDigest also participates in recovery. Before activation against existing data, use an authorized offline compatibility audit to establish those identities were written with compatible en-US collation. Existing cs/sk records cannot silently be treated as en-US. If a mismatch exists, hold activation for a separately reviewed compatibility/recovery design; do not clear claims, regenerate deployment identity, rewrite immutable rows, or grant permission via a fallback hash. This patch performs no data audit or migration. Compatible en-US identities require no schema change or new deployment; on-chain redeployment is not a remedy.

Frontend coordination: Claude owns planner canonical/digest. It must use the same explicit en-US rule and golden vectors; backend-only repair does not fix an unfixed cs/sk browser. The separate bare `?`/`#` submission API base bug is frontend work and is outside this patch. No signing, RPC, database, activation or deployment behavior is added.

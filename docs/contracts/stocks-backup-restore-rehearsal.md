# Stocks 데이터베이스 백업·복원 리허설

## 사용 방법

`stocks:setup`으로 준비한 작업 폴더에서 다음 명령을 실행한다.

```sh
npm run stocks:recovery:check
```

기존 사용자 DB나 실행 중인 `stocks:dev`에 연결하지 않는다. 실행 도구가 새 Unix 소켓
전용 PostgreSQL을 만들고 테스트 데이터로 백업·복원을 검증한다. 실제 운영 백업을
만들거나 현재 로컬 거래 기록을 저장하는 명령이 아니다. 외부 DB 주소는 입력받지 않는다.
PostgreSQL 서버와 같은 설치의 `pg_dump`, `pg_restore`, `dropdb`가 필요하다.
Node·Corepack·의존성 검사 후 서버와 계약을 빌드하고 고정된 DB 테스트 목록을 실행한다.

## 검증하는 순서

1. 검토된 Stocks 마이그레이션을 새 DB에 적용하고 DB 통합 테스트를 실행한다.
2. 매수·매도 주문, 확정된 제출 기록·증거, 운영자 재개 후 중지 이력을 준비한다.
3. PostgreSQL과 검증 프로세스를 다시 시작해 기존 복구 검사를 수행한다.
4. 모든 테스트 클라이언트가 끝난 상태에서 테이블별 행 수·내용 해시와 DB 규칙을 기록한다.
5. `pg_dump`의 custom archive를 만들고 새 `submissions_restored` DB에 단일 트랜잭션으로 복원한다.
6. **이 리허설이 생성한 원본 `submissions_test` DB만 제거한다.** 원본 연결에 의존한 통과를 막는다.
7. 새 DB에서 모든 행, 마이그레이션 이력, 열·제약·인덱스·트리거·함수·시퀀스 정보를 비교한다.
8. 원래 주문 복구, 제출 증거, 중복 claim 방지, 운영자 중지·이력·재요청 멱등성을 다시 확인한다.
9. 소유 DB를 종료하고 백업 파일을 삭제한다. 실패·취소도 동일한 정리 절차를 거친다.

행의 순서가 바뀌어도 비교할 수 있지만 행 내용 변경·누락·중복은 실패한다.
PostgreSQL 자체의 제약식 출력 기능을 사용해 복원 시 생기는 동치 괄호 차이를 정규화한다.
SQL 문자열에서 괄호를 임의로 제거하거나 논리식을 느슨하게 비교하지 않는다.

## 성공 판정과 기록

프로세스 종료 코드0과 다음 표식 모두가 필요하다.

- `STOCKS_BACKUP_RESTORE_SNAPSHOT_PASS`
- `DATABASE_BACKUP_RESTORE_PERSISTENCE_PASS`
- 최종 `OWNED_PG_EVIDENCE`가 가리키는 JSON의 `stopped: true`
- `backup.created/restored/sourceRemoved/verified/archiveRemoved` 모두 true

GitHub의 `Stocks / postgres` 작업도 위 조건과 백업 해시·파일 크기, 원시 백업 파일 부재,
DB 프로세스·소켓·PID 파일 부재를 확인한다. 성공 문자열 하나만으로 통과시키지 않는다.
백업 생성, archive 검사, 복원, 원본 제거, 비교 중 하나라도 실패하면 성공을 기록하지 않는다.
취소는 취소 종료 코드로 반환하며 성공으로 바꾸지 않는다.

로그에 출력하는 복원 요약은 테이블/행 수와 규칙 해시다. 행 원문과 백업 파일은 외부에
내보내지 않는다. 진단용 임시 폴더에는 종료된 테스트 DB와 해시 기준표가 남을 수 있다.
이 폴더를 운영 백업으로 사용하거나 통째로 업로드하지 않는다. 별도의 자동7일 삭제 정책은 없다.

## 공개 테스트 환경에 적용할 때

이번 검증은 동일 PostgreSQL 버전의 논리 백업을 별도 DB로 복원하는 리허설이다.
운영 백업 저장소·암호화·접근 권한·보존 기간·시점 복구·버전 간 업그레이드 검증을 대신하지 않는다.
마이그레이션 이력은 이 테스트의 fixture이며 Prisma 배포 자체를 검증했다는 의미도 아니다.

실제 복구 시에는 신규 거래를 차단하고 API·worker의 쓰기를 정지한 뒤 원래 배포 명세,
DB 백업 시점, 관찰 체크포인트, 외부 서명 서비스의 영속 작업 기록을 확보해야 한다.
격리된 복원 대상에서 검증을 마치기 전에 서비스 DB를 덮어쓰거나 거래를 재개하지 않는다.
역할·권한은 별도로 적용한다. 이 리허설의 `--no-owner --no-privileges`는 운영 권한 복구가 아니다.

DB를 과거로 복원해도 이미 전송한 체인 거래는 되돌아가지 않는다. 기존 signer의 원래
작업 식별자·nonce·hash를 조회하고 백업 이후 체인 이력을 다시 관찰해 원장과 대사해야 한다.
확인되지 않은 전송을 새 전송으로 대체하지 않는다. 현재 관찰과 대사가 일치하고 미확정
전송의 복구가 끝난 뒤 운영자가 거래 재개를 결정한다.

공개 호스팅/DB 대상과 외부 서명 서비스가 제공되면 해당 환경에서 별도의 복원·대사·재개
검증을 수행해야 한다. 관련 설정은 [서버 연결과 활성화](stocks-giwa-runtime-activation.md)를 따른다.
